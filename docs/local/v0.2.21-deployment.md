# v0.2.21 上线与回退流程

需求：[TOO-703](https://linear.app/sisyphus-sq/issue/TOO-703)。适用机器：sqmc03（生产）+ sqmc05（候选验证）。本文件是执行流程，不是上线回执；本轮没有合入 stable、发布镜像或部署生产。

## 当前事实与进入条件

2026-11-11 的 sqmc03 只读检查确认：

- 应用镜像 `localhost/sub2api:v0.2.20-ceb7c47a`，镜像摘要 `sha256:42c701a3d993b3a9ecc1158e3e68258e903d28e3c54416275253643538518d55`。
- 应用内存上限 1 GiB；`GATEWAY_REQUEST_BODY_MEMORY_BUDGET_BYTES=536870912`，即 512 MiB。新版自动预算最低仍为 1 GiB，上线时保留显式配置。
- 数据库已有 301 条迁移，文件名和校验和全部与候选源码一致；只缺下列两份迁移：
  - `249_add_usage_logs_api_key_cost_index_notx.sql`：为 `usage_logs` 创建并发覆盖索引。
  - `250_openai_cache_write_ttl.sql`：新增两种缓存 TTL 用量及四处 12h 缓存写入价字段。
- PostgreSQL、Redis 和应用在本轮检查期间没有重启。执行上线前必须重新检查这些事实。

进入部署前，先审查候选 PR、回读对应提交的 CI，并由用户确认推进 `suqing/stable` 及部署。使用最终被接受的固定提交；不能将本地测试二进制直接当作正式镜像。验证范围和实际结果见 [TOO-703 验证记录](too-703-verification.md)。

## 1. 确认机器、源码和固定产物

跨机器操作先用 `tailscale status --json` 按 `HostName` / `DNSName` 解析 sqmc03 当前地址，不使用历史 IP。沿用 SSH 用户 `suqing`、已有密钥、严格 known_hosts 校验；sqmc05 已确认的主机身份别名为 `sqmc03.local`。

在隔离构建目录检出最终被接受的完整提交，使用项目锁文件和 Go 1.27.3 构建前端与 Linux arm64 嵌入前端的后端。源码 `VERSION` 为 `0.2.21`；正式产物仍显式注入 `main.Version=0.2.21+sq.<短SHA>` 和 `main.Commit=<完整SHA>`，并用 `-version` 回读。

优先按既有固定基础镜像流程打包，记录基础镜像摘要、源码提交、平台、产物 SHA-256 和最终镜像摘要。镜像名使用 `localhost/sub2api:v0.2.21-<短SHA>`，不使用 `latest`。镜像构建、打包和版本检查属于发版步骤；提交收尾不重复运行已完成的测试。

部署配置只在 sqmc03 的 `/Users/suqing/.config/sub2api/deploy.env` 维护，权限保持 600；不要复制到 sqmc05 或写入 Git。保留 PostgreSQL、Redis、数据卷、JWT/TOTP 密钥及现有业务配置，仅按审查结果切换 `APPLE_CONTAINER_SUB2API_IMAGE`，并确认 512 MiB 请求体预算仍有效。

## 2. 用生产快照演练迁移与旧镜像回退

先从生产获得一致的 PostgreSQL dump，并记录迁移历史和账本/余额/Key 配额基线。快照及所有凭据保存在 sqmc03 私有备份目录，目录 700、文件 600。

将快照恢复到独立数据库、Redis、网络、端口和应用卷；测试环境不得连接生产数据库或沿用生产入口。清除或禁用测试副本里的自动任务与真实上游凭据，避免副本发起业务请求。

在副本上启动固定的新镜像，通过项目迁移器完成 301 → 303：原 301 条校验和不变，新增两份迁移；重复启动不增加记录。并发索引必须在事务外运行，检查 `idx_usage_logs_api_key_created_cost` 的 `indisvalid`、`indisready` 均为 true，并记录与生产数据量相当的实际耗时。

随后在同一升级副本上启动保留的旧生产镜像，验证启动、账单读取及关键业务读取。新的列和索引属于添加式变化，但源码审查和空测试库验证不能代替这一步。生产规模的建索引耗时与旧生产镜像回退演练完成前，不进入维护窗口。

## 3. 维护窗口与备份

1. 保存当前 Tailscale 8080 转发配置、容器名称/镜像摘要、依赖容器启动时间和命名卷信息；输出先过滤环境变量。
2. 暂停现有 8080 外部入口，等待在途请求归零，不中断正在计费的请求。
3. 保留 PostgreSQL、Redis 运行，仅停止应用 `sub2api-apple`。
4. 在 `/Users/suqing/.local/share/sub2api/backups/v0.2.21-<日期>-<短SHA>/` 保存配置、应用卷、PostgreSQL dump、Redis RDB，以及迁移、余额、Key 配额、账单/去重数量基线；核对备份大小与校验和。
5. 保存旧固定镜像和配置副本。不要执行卷删除或数据库清空命令。

## 4. 只替换应用

在 sqmc03 固定源码提交的部署入口执行：

```sh
SUB2API_ENV_FILE=/Users/suqing/.config/sub2api/deploy.env \
  /Users/suqing/Coding/golang/00_self/sub2api/deploy/apple-container.sh up
```

当前脚本的普通 `up` 会复用运行中的依赖和现有命名卷，重建应用容器。不要使用 `up --recreate`、`restart`、`down` 或 `destroy`：这些入口会重建或停止数据库/Redis，或者删除资源。

等待迁移和健康检查结束；并发索引可能因历史长事务或数据量耗时，不能仅因启动较慢就重放迁移。超时时保留日志和数据库现场，先检查锁等待及索引状态；项目迁移器已包含清理无效索引后再建的处理。

## 5. 上线后验收与恢复入口

- 回读应用版本、完整源码 SHA、镜像摘要、512 MiB 预算、健康接口和嵌入前端。确认 PostgreSQL/Redis 启动时间及三个命名卷未变化。
- 迁移历史必须为原 301 条不变、新增两条；索引有效。核对维护前后的业务基线，没有请求时不得出现账单或余额变化。
- 在明确的生产验收账号与预算下，少量验证百炼 TTS、Decisions、生图及账单/余额/Key 配额与去重。先记录请求意图；超时或未知结果先查账，不盲目重放付费请求。内部扣费与供应商账单分别记录。
- 检查账号、用量、价卡页面和新 TTL 字段。恢复原来的 8080 入口，从 sqmc05 验证入口可达，再观察错误率、并发、延迟、内存与新增账单。
- 将实际产物、迁移、窗口、验证、费用、回退材料和未覆盖项写入部署回执。部署成功与候选测试通过分别记录。

## 6. 回退边界

应用或关键账务异常时先暂停入口、等待在途归零，保存升级后的数据库及新增账本，再停止新应用。若第 2 步已证明旧生产镜像兼容升级后的库，可将配置切回保留的旧镜像，使用普通 `up` 替换应用，保留升级后的数据库和所有新账单。

不执行反向 DDL，不改历史迁移文件，也不直接用维护前的旧数据库覆盖现库。上线后已产生新写入时，旧备份会丢失账本、余额和配额变化；若必须恢复数据库，先制定并审查包含新增数据的恢复方案，不能自动回滚。旧镜像无法兼容升级库时保持入口关闭，优先修复或采用已演练的恢复方案。
